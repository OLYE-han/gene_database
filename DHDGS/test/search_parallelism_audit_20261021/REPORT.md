# 搜索并行性与锁核查（2026-10-21）

基于已有并发扫描00_c256与03_c2048的原始分支记录，不新增性能测试、不修改搜索代码。每节点分别核验clock_domain，按native_search_start_ns至native_loop_done_ns扫描重叠区间；线程CPU时间来自server_thread_cpu_ms。

|案例|节点|不同搜索线程|峰值重叠区间|平均重叠区间|搜索CPU等效核数（近似）|
|---|---:|---:|---:|---:|---:|
|00_c256|0|64|64|26.56|26.51|
|00_c256|1|64|64|28.04|27.79|

|03_c2048|2|64|64|13.83|13.79|

节点0/1/2对应Intel-35/32/30。峰值区间重叠不代表64个线程同一时刻全在CPU执行；CPU等效核数=累计搜索线程CPU时间/该节点首个搜索开始至最后搜索循环结束窗口。CPU计时范围略宽于搜索循环区间，因此是近似值；仍足以排除全局单线程串行搜索。此值与以管理快照窗口计算的进程CPU核数不同。

源码核查：native_pool.hpp取出任务后退出队列锁再执行fn；native_runtime.cpp::run不持有DataRuntime::mu执行搜索；search_loop.hpp查询候选/去重/结果/读取缓冲为局部对象，sync_pread使用显式offset。原生路径不会逐批回到Python，也无全局搜索互斥锁覆盖距离计算。

仍存在接纳状态锁（注册控制器也在其内）、计算队列锁、控制命令队列锁/控制状态锁、网络队列锁和分支trace锁。控制器单线程持state_mu推进命令/定时器/派发准备，可能导致注册等待或完成报告排队；这不等于各查询图搜索被串行。ManagedTransport gate为共享锁，并不让正常查询互斥。建图graph_locks不是只读检索路径的锁。

当前资料未测出每把锁的完整等待/持有分布，不能断言锁没有成本，也不能断言某把锁是吞吐上限原因。优先补齐接纳、控制注册、完成命令排队及网络事件循环的局部时间戳和队列占用，再做单因素消融。搜索线程翻倍未提速可由其他阶段容量、共享CPU/缓存/内存资源或负载分布解释，不等于没有真正并行。
