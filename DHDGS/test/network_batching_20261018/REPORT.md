# 网络请求聚合：离线机会评估

本次完成设计与历史事件回放，**没有修改运行时发送协议，也没有运行真正的批量RPC**。结果用于选择后续实验参数，不能当作吞吐或延迟提速。

来源为 `wait_latency_20261018/fastoff/runs/20261018T200500/report.json.gz`：完整seq_2M、本机三TCP数据进程、2000个查询、全局预算200。共695次被扩展函数批准的跨数据节点派发，每个父分支至多一次派发且无重试，因此现有标量入队时间戳可以无歧义映射到每个动作。总协议RPC为5455次，其中还包括2000次根提交和结果/心跳等消息。

回放以每个source→target的最老任务启动窗口，后续任务不会延长窗口；达到16条或估计256KiB则提前封闭。本轮8条和16条上限结果相同，因为实际形成的最大批只有6条。

六条通信方向分别有：0→1为220次、0→2为1次、1→0为98次、1→2为157次、2→0为8次、2→1为211次。不同目标不能装进一个直达RPC。2000个并发查询并不等于每个目标在任意0.2ms窗口内都有很多已批准派发；当前上游处理也会使任务到达分散。

**解释：** 聚合可以减少RPC及固定处理开销，但短窗口在当前派发流量中只有有限聚合机会。0.2ms窗口的642批中591批仍只有一条；这些单项批可能只增加凑批等待。不同查询的向量数据仍需各自发送，不能将RPC下降比例称为字节下降比例。仅优化派发也无法移除入口提交或结果回传RPC，因此不能直接解决已有数百毫秒的接纳积压。

模拟没有纳入真实发送队列、连接池、接收处理、GIL/OS定时精度和执行反馈；实际额外延迟可能超过设定窗口。0ms模拟立即发送，不代表实际opportunistic模式的收益：后者可以利用已有发送积压顺便合并，需要真实实现对照。使用独立请求编码长度加128字节预留作为大小估计，没有生成批量编码，也没有声称节省多少字节。

建议实际验证off、不主动等待的opportunistic、0.1/0.2/0.5/1ms窗口，优先p99并同时测QPS、召回、失败及各队列。批量最大8/16条、256KiB；取消/续租不加入普通窗口。全部设计、协议错误处理和计数口径见 [DESIGN.md §11.14](../../DESIGN.md)。
