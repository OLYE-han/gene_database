# 计算线程数对照实验（2026-10-20）

问题：增加数据节点搜索工作线程，能否在同等负载下提高 QPS，并减少接纳排队？
本实验不预设纯搜索计算已是瓶颈。原慢样本的接纳队列等待远大于搜索墙钟。

固定：完整 seq_2M 索引、三个数据节点、客户端并发256、top-k10、全局预算200、
顶层4个查询所属进程（每进程1路由线程/4派发线程）、相同查询顺序和真值、
RaBitQ/跨机扩展/逻辑I/O参数、完整指标与日志、60秒去重保留及131072条容量。
唯一搜索参数变量为 `peer.worker_threads`：32、64、128，每台数据节点统一取值。

短测：每轮10000请求（固定2000查询重复5次，身份不同），预热32请求；顺序
32→64→128→64→128→32→128→32→64，各3轮。报告逐轮值、QPS和p99中位数，
不以单轮峰值选型。要求无失败、平均Recall@10至少95%、预算与不重访审计通过。
按QPS中位数选出64/128中较好的配置，即使均弱于32也执行后续反证对照。

长测：100000请求/轮（固定2000查询重复50次），32→候选→候选→32，
每组两轮；报告连续吞吐与每10秒完成数、尾延迟、就绪队列、每查询搜索CPU、
各节点CPU/物理读取/GC累计增量及保留窗口内的节点细分时间戳。
若短测收益无法在两轮长测中复现，不能称为持续吞吐优化。

每轮重新启动独立测试数据进程和入口，复用索引；保留原常驻服务。
所有配置使用相同的当前冻结Python源码，校验远端原生模块对应的C++源码一致。
新进程重置记录积累和GC历史，重复次序平衡共享机器负载、缓存等时间因素。
不清空OS页缓存；这是热缓存检索实验，不是冷SSD吞吐试验。

运行前按用户要求清理历史重复存储：无损归档1136个文件，释放约10.83GiB。
因此所有组仍将工作进程日志写在原NVMe上的本实验temporary_logs目录；每轮
结束后无损压缩并核对SHA256，再移除该轮临时未压缩副本，保留压缩件。
原/tmp暂存方案未投入计时实验。数据路径、逻辑I/O后端及日志存储设备保持一致。

阶段时间戳只在同一主机内相减；分支累计等待不除以端到端时间当作互斥占比。
结果应区分线程容量不足、接纳/控制调度及实际搜索计算；增线程的收益或无收益
本身不足以证明某一内部原因，结合CPU工作量、队列和GC证据判断。
