# 固定搜索线程的等待定位与自适应控制实验

搜索计算固定每节点32线程，预算200，客户端并发256，完整seq_2M，三机，顶层4个查询所属进程。维持召回>=0.95、零失败及预算/节点访问审计。

第一阶段同一冻结源码新增消费者队列锁请求/取得、是否曾等空队列、消费者CPU时间戳，比较shared锁1消费者、shared锁4消费者、独立锁1消费者、独立锁4消费者，各10000请求。分析全部分支（如保留窗口过期则报告覆盖率），不把CPU空闲等同无GIL/锁竞争，不跨机器对齐时钟。

第二阶段依据第一阶段决定动态控制范围。仅改变已获批准任务的控制服务资源，搜索线程数、预算、扩展函数、召回条件不变。队列等待必须联合下游压力、服务完成率评估，扩容要有上限，低压力缩容要有滞后。不把等待迁移到下一队列当成优化。保留静态最佳对照与动态对照，连续负载验证历史状态积累影响。

此前100000请求线程扫描在用户中断后未形成有效结果；已确认父benchmark退出，通过管理接口只关闭三个已空闲的实验节点。旧常驻集群未停。所有结果写本目录；性能测试串行，分析与压缩在计时结束后运行。

诊断后变更（已按证据转向）：仅增加消费者使状态锁争用加重；取消提交的多余全局锁使就绪队列大幅下降，但远程派发连接等待变为长尾主因。因此v4保持每节点32搜索线程、16固定远程发送线程、独立单接纳消费者和分支专属提交，比较data FIFO固定2连接与FIFO动态2..8连接，按A-B-B-A交错执行。最后一轮单独关闭lane重复JSON日志，root完整queries.jsonl.gz/CSV和节点指标仍保存。固定线程与动态线程的失败尝试保留作为消融证据，不能把队列搬家当成功。

source/source_v2/source_v3/source_v4为独立冻结源码；所有计时结果必须与各自plan.yaml及loaded_sources.json一起解读。v3原计划后追加的09..11变体未执行，后续优先验证已明确的连接等待，不把计划条目当实验结果。生产常驻集群不替换。

中断记录：第19轮在数据启动阶段被会话中断，没有开始有效benchmark，结果目录保留interrupted.json；逐节点确认空闲后已关闭遗留测试数据进程。20..22计划项未运行。v5的18轮只作为单次探索，不冒称已完成ABBA。

最终v6对照：新增O(1)租约身份查询（语义不变）、Python池化RPC TCP_NODELAY独立开关、顶层入口连接自适应开关。先重测原配置，再以nodelay与双侧自适应网络容量按B-C-C-B交错，各10000请求；最后用8个顶层所属进程作一次容量诊断，数据节点搜索线程仍32。不同源码快照及不同进程数结果分别列出，不合并成单变量收益。

持续验证：旧source快照（原lease全表扫描）与source_v6（O(1)lease、默认不启用实验性扩容）各100000请求。两者不是逐行仅差lease：v6另包含未启用的可选机制、细化时间戳及独立pending计数锁；报告将称为“默认实现整体对照”，不把全部差异强行归因于O(1)。每轮新数据/head进程，显式记录实际加载source路径，启动时间不计入QPS。19/20..22未完成或未运行的计划不进入统计。
