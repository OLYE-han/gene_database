# QPS差异的受控实验

固定：完整2M×2560D索引、同一2000条validation查询、L2/top-k10、预算200、remote_weight=1、每数据节点32个查询工作线程、总客户端并发128、native搜索/native控制、sync_pread、预热32。主测试不修改生产代码及正式服务参数。

## 竞争解释

1. **比较条件不同**：历史高QPS单机测试用20个独立入口进程；新部署用一个持久head。旧发生器不仅改变GIL数量，也将每节点入口连接池总容量从2增加到约40。历史成绩不能直接当作物理网络开销的基线。
2. **入口连接池等待**：旧主测试逐query记录显示pool_wait均值339.86ms，占全部客户端延迟之和91.43%；最慢query的4.723秒中4.678秒在取入口连接。最慢查询只访问Intel-35本地data-0，没有跨节点分支。
3. **真正的物理拓扑损耗**：机器CPU、网络RTT、回传、共享SSD/内存带宽等需要同参数实测；不能由总QPS倒推。
4. **计算/SSD瓶颈**：需要同时检查原生计算时长、就绪排队、逻辑读取与物理磁盘增量。少量查询就绪等待不能代表系统总等待。

## 主矩阵

2种物理拓扑 × 顶层入口每目标连接容量2/16/64 × 3轮 = 18组，每组2000条查询，共36000条正式查询。

- local：三个独立数据进程均在Intel-35，使用21251/21252/21253端口。
- remote：复用现有Intel-35的data-0、Intel-30的data-1/data-2。原生产head在实验期间空闲。
- 两组实验head均是Intel-35上单独启动的一进程、128客户端工作线程，调用同一ClusterHead.benchmark代码。回调端口21280。
- **只修改实验head实例的入口连接池capacity**。数据节点→其他节点和数据节点→head的连接数仍为原始2；执行签名、搜索参数不变。额外参数记录在各case.json中，不假称修改了生产YAML的peer通信参数。
- 交替拓扑和容量顺序，检查漂移；每组均报告召回、失败、预算、重访、计算与逻辑/物理I/O，避免通过改变工作量换取QPS。

每次RPC占用入口连接直到数据节点接纳ACK。每目标2条连接、3个目标合计最多6条在途**入口提交RPC**，不表示只能同时运行6条查询。`pool_wait_ms`包含连接池锁/条件变量等待、唤醒后的调度以及连接健康检查耗时；不能把它解释为网络传播时间或仅仅某一把锁持有的时间。

QPS只计正式查询窗口。head_process.before/after用于进程资源证据，覆盖预热与结果采集/序列化，其窗口比QPS窗口更大，不能直接当作测量窗口CPU利用率。

原始数据在cases/<topology>_p<capacity>_c128_r<repeat>/。temporary local节点由finally停止；生产集群保留原来的32线程、并发128与预算200。实验前后生产status均归档。

## 根据主矩阵追加的验证

- 单机/两机分别3轮20入口进程实验（每轮2000，总并发仍128，线程分配为8×7+12×6）。各进程独立HNSW/连接池/GIL/回调端口；总预热32。此项检验旧式入口布局，不是单纯的GIL开关。每目标入口连接总容量变为40，数据节点可向20个回调端点发送，不能只把改善归因于增加CPU核数。
- 两机另起临时节点，仅通过实验启动器将原生NativeController的回传连接数从2改为16；数据→数据连接池仍2，head入口池64，搜索签名/算法/预算不变。3轮，每轮2000。额外容量在case.json与启动日志中明确记录。此变量不冒充生产YAML热参数。
- 2条/64条入口连接各一轮CPU剖析。覆盖正式查询前后近似窗口，包含工作线程启动与最终排空、排除预热和快照序列化。记录进程用户态/内核态CPU秒，以及head回调接收/处理线程CPU。插桩组单独展示，不混入原3轮性能中位数。

主矩阵36000 + 多入口12000 + 回传6000 = **54000正式查询**；CPU剖析另4000条。全部顺序执行，无两个负载实验重叠。最后核验正式生产集群参数/进程及临时节点清理状态。
