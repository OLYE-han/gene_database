# 全量三机计算线程数实验

## 目的与变量

观察每台数据节点 `peer.worker_threads = 1, 2, 4, 8, 16, 32` 对检索性能、召回和资源利用的影响。
使用 Intel-35、Intel-32、Intel-30；入口和发压进程仍位于 Intel-35。
客户端闭环并发固定为 8 和 32，分别横向比较六种线程配置，不能把不同并发下的 p99 作为线程收益。
线程数表示线程池容量，实际活跃线程数受查询数、路由分布、GIL 和等待影响。

## 固定条件

- 完整 2,000,000 × 2560 索引，复用已验证的三个分片，不重新建图。
- 同一批 1,024 条验证查询，各配置恰好运行一次；总计 12,288 个计时请求。
- 原始 L2，1-bit RaBitQ，top-k=10，扩展预算 1024，候选池 256，本地 beam=4。
- BLAS=1，同步 pread，应用缓存为零，详细追踪开启，监听队列 128。
- 保留既有扩展决策、预算分配、单节点不回访和入口职责。
- 每个客户端预热 2 次，预热、加载、SSH、哈希验证和结果压缩均在计时窗口外。
- 复用系统页缓存，不清空共享机器缓存；报告实际物理读取字节。
- 每种线程数重新启动数据服务；同一线程数下两档并发共用该服务实例。
- 预先固定顺序 1 / 8 / 2 / 32 / 4 / 16，客户端并发顺序交替，避免线程数与时间单调相关；这不替代重复测量。

## 记录与判定

逐查询保留延迟、Recall@10、网络字节与 RPC、跨节点分支、逻辑文件字节与 pread 次数、距离计算与 CPU 时间、扩展次数与路径深度、备用入口使用和控制错误。
保存端到端阶段均值及逐查询阶段耗时、每节点 CPU / RSS / 物理 I/O 采样、构建信息引用。
其中累计子阶段时间与端到端时间不同；纯网络与纯 SSD 等待尚不可独立识别，不能虚构占比。

检查预算守恒、节点不回访、入口不执行中间扩展、每次跨机派发有决定函数批准、结果去重、查询身份一致和指标完整。
失败或指标不完整的配置保留原始记录，在推荐时排除。累计指标均值使用指标完整的成功查询，明确标记样本数。
召回均值使用所有请求，失败查询按零召回计；成功 QPS 与成功请求延迟继承现有 benchmark 定义。

同一客户端并发下，先筛选平均 Recall@10≥0.99、零失败、指标完整的配置，再优先最低 p99，其次 QPS。
本轮为单次参数扫描；差异小的配置需要后续复验，不能宣称全局最优或线性扩展。
本轮复用已有验证集做性能比较，不提供新的独立泛化召回验证。

## 文件与运行

所有参数在 `experiment.yaml`；生成的节点和请求配置作为快照保留。
`run_experiment.py` 复用现有部署与 benchmark，不修改搜索实现。
原始 `report.json` 与 `queries.jsonl` 在每组结束后压缩并校验解压哈希，以控制 SSD 占用。
`comparison.csv` / `comparison.json` / `SUMMARY.md` 随完成的组更新；只有全部服务确认退出后才生成 `completed.json`。

在本目录执行：

```sh
../../.venv/bin/python run_experiment.py --validate-only
../../.venv/bin/python run_experiment.py > execution.log 2>&1
```

初始 SSH 准备失败日志保存在 `preflight_attempt1/`，没有计时查询，不计入性能结果。
重试使用 SSH 连接复用；查询协议与超时配置不变。
