# 为什么增加工作线程后变慢

本轮扫描完成 12 组、12,288 个计时请求。每台数据节点是一个 CPython 进程，`peer.worker_threads` 调整该进程的 `ThreadPoolExecutor`，没有增加工作进程或 CPU 核数。当前解释器启用 GIL；同一进程内同时只能有一个线程执行需要 GIL 的代码。三台服务器各自有独立解释器与 GIL。

源码证据：工作线程池见 [peer.py](../../python/dhdgs/peer.py#L223)，图搜索循环见 [peer_search.py](../../python/dhdgs/peer_search.py#L81)，读与扩展见 [index.py](../../python/dhdgs/index.py#L365)，释放 GIL 的 RaBitQ 内核见 [native.cpp](../../cpp/native.cpp#L140)。

## 读可以并行，等待发生在哪里

`os.pread(fd, size, offset)` 位于应用缓存锁之外，使用显式偏移，不共享 `seek` 文件位置；CPython 在阻塞读取期间释放 GIL。因此这里没有一把应用锁把所有读操作串行包住。同一查询的同步循环仍逐条读取；不同工作线程的读取可以重叠。

但 Python 在读调用返回后必须重新取得 GIL，才能记录时间、解码向量、收集邻居和推进搜索。当前 `pread_ms` 的起止计时在 Python 层，因此覆盖系统调用及返回 Python 的调度等待；不能直接视为设备服务时间。整个扫描的进程物理读取统计均为零，逻辑读取由热页缓存服务，本轮不能据此评价冷 SSD 并行能力。

RaBitQ C++ 评分循环显式释放 GIL，部分 NumPy 运算也可在原生代码执行。这允许部分计算并行。但输入检查、数组与 Python 对象构造、邻居遍历、候选排序、搜索决策、指标与 trace 维护等仍有需要 GIL 的区间。每次小块 I/O 或原生运算完成，线程都要重新竞争解释器执行权。

## 共享资源及证据边界

| 资源 | 当前实现 | 能得出的结论 |
|---|---|---|
| 每进程的 GIL | 搜索主循环仍是 Python；计算、控制和传输线程属于同一进程 | 存在结构性并行限制；尚未直接测出 GIL 等待占比 |
| 分片缓存与统计锁 | 缓存查找/LRU、统计更新共用锁；监控快照也使用该锁 | 存在额外同步；锁不覆盖整个 pread 或搜索。应用缓存关闭时仍进入缓存锁，可优化但未证明是主要耗时 |
| 查询生命周期锁 | 分支登记、状态与控制信息更新 | 有短临界区；各分支的候选集与结果集不是全局共享候选队列 |
| CPU 调度和对象管理 | 多线程切换、Python 临时对象、排序、详细 trace | 更多线程可能增加单位查询 CPU 工作；需要 profiling/消融才能细分 |
| 缓存、内存带宽、NUMA | 不同线程读取编码、邻接与向量，创建临时数组 | 可能影响性能；本轮没有硬件计数器证据证明它们饱和 |
| SSD / 网络 | 物理读取为零；所选慢查询无跨节点搜索 | 无证据支持 SSD 或跨机带宽是该查询长等待的主因 |

## 同一查询的直接证据

查询 ID 264815，固定客户端并发 32，两种配置均扩展 1,024 个顶点、Recall@10=1，仅在 Intel-35 搜索。

| 每节点线程 | 端到端 ms | 分支执行墙钟 ms | 搜索线程 CPU ms | CPU / 分支墙钟 |
|---:|---:|---:|---:|---:|
| 1 | 4294.418 | 184.877 | 175.816 | 95.10% |
| 32 | 10921.509 | 10893.564 | 764.609 | 7.02% |

一个工作线程时，请求主要在进入搜索分支前排队。增加工作线程后，更多请求进入搜索分支，同时竞争解释器和其他共享资源；排队位置变化，实际处理容量没有同步提高。该查询的线程 CPU 时间还增至约 4.35 倍，说明除了等待，还增加了执行开销。具体开销来源尚未用 profiler 分离。

32 线程时分支墙钟减去本搜索线程 CPU 时间约为 10,129 ms，表示该线程没有在 CPU 上执行的时间；其中可能包含 GIL、调度、锁、I/O 等等待及其他线程执行的工作，不能把差值全部命名为 GIL 等待。

整组结果同样退化：固定客户端并发 32，1 → 32 工作线程，QPS 9.02 → 2.47，p99 9.46 → 32.31 秒；三个数据进程平均用核数合计 2.56 → 1.90。没有出现“更多线程充分利用更多核”的情况。单查询调度有波动，完整扫描见 [ANALYSIS.md](ANALYSIS.md)。

## 后续优化与验证顺序

1. 在固定查询、并发与预算下采集 GIL/off-CPU、线程调度、应用锁等待和队列时间；对详细 trace 做开/关消融。避免将观测代码自身的开销误归为算法成本。
2. 将批量读取后的解码、距离计算、邻居收集和候选维护连同搜索热循环移入 C++，以较大工作块释放 GIL；保持现有跨节点扩展决策与查询预算语义，再重新扫描线程数。
3. 可对照多工作进程方案，共享只读 mmap/编码数据，测量额外内存和 IPC 成本；不能默认每进程复制完整索引。
4. 应用缓存关闭时跳过无用缓存锁，线程局部累计指标后汇总，缩短监控临界区；通过独立消融评价收益。
5. 冷数据集下再比较同步与异步 SSD，记录真实设备读取、队列深度与完成延迟。热缓存下的解释器争用不能靠增加 SSD 并发解决。

以上是下一轮建议，本轮没有修改搜索算法或默认线程数。延迟分解与时间轴见 [查询报告](query_latency/README.md)，图中各段为包含等待的代码墙钟区间，不是纯硬件资源耗时。
