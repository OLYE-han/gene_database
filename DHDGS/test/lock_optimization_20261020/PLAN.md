# 锁优化验证

阅读LOCKS.md后，本轮聚焦D1→C1/C2嵌套等待、持锁期间对象清理与H8输出IPC锁的观测。

每数据节点固定32搜索线程，完整seq_2M三机，客户端并发256、预算200、top-k=10；预热32，验证查询固定2000条循环。保持搜索/远端扩展/去重/预算与结果指标完整性，不改变GC策略。

使用同一冻结源码、同机编译的二进制，比较：baseline（两个开关均关闭）、gil（仅native注册释放GIL）、split（再将原生注册移出Python状态锁，清理对象移出该锁）。短测各10k，顺序baseline/gil/split/split/gil/baseline。长测各100k，计划baseline/split，依短测及正确性结果决定是否执行；不把计划当作结果。

split协议先原子预留身份及active/pending额度，锁外注册，再锁内提交。匹配重试在锁外等待同一Future；失败、取消、关闭与过期有回退路径，不提前成功ACK。新增故障注入覆盖各边界。

同源基线也包含新的观测：native注册的C1/C2等待、Python预留/注册/提交边界、lane结果打包和写锁时间、父进程接收和解码时间、benchmark父进程GC事件。与上一轮不同源码的绝对性能不当作单因素收益。

三机独立实验端口29751–29753，顶层回调29810起。常驻220xx集群保留。构建、回归、数据解析不与性能计时重叠；worker重复日志压缩校验后归档。至少要求零失败、Recall@10>=0.95、协议审计通过；比较完整QPS/p99及所有等待，局部队列下降不是整体优化完成。

实际完成：短测10–15号六轮，持续对照00_baseline/01_split两轮，共260000正式请求，全部成功且质量/协议检查通过。首次short/00_baseline因Intel-30运行库不匹配只有启动失败，不计入实验；改用系统g++重建并验证import后重启。406项回归通过。

结论：没有证据支持默认启用完整拆分；保持两个开关false。锁临界区显著缩短，但全链路等待受GC及调度影响。详细数据、采用决定和时间线见[REPORT.md](REPORT.md)。本地新模块已原子替换安装，常驻旧进程未重启；三机实验监听已关闭，最终状态见final_cluster_check.json。
