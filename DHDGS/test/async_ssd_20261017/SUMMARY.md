# 节点内异步 SSD 首阶段实现验证（2026-10-17）

已实现 resumable 查询、节点内独立记录批量提交、原生 io_uring 和有界 I/O 线程池；同步 blocking 保留默认。I/O 通知只恢复本地计算，不直接派发远端查询。

## 验证结果

- [最终回归日志](unit_tests_eventfd.log)：57 项测试全部通过，启用了真实 io_uring 和三进程 TCP 测试，没有跳过项。
- 覆盖整轮大于 I/O 深度、完整缓冲预约、背压拒绝、短读、epoch、取消后的迟到读、乱序完成、跨查询提交、缓存命中和实际记录/精确距离/邻接一致性。
- 单计算线程测试用受控阻塞读取证明两个查询可以同时等待 I/O；固定动作的异步/同步扩展 ID 和距离一致。
- 本地轮次暂停期间，远端候选的等待阈值经过仍不产生新分支；本轮消费后进入正常决策点，才出现带 decision ID 的派发。
- [最终审计](verification.json)：768 个成功请求，预算守恒、每节点最多一个后继、零节点回访、零顶层 expand RPC；逐轮 token/字节和分支状态时间核对通过；服务均已停止，最终源码哈希与实测一致。

## 实测配置

同一 4096 × 2560 L2 pilot 索引、1-bit RaBitQ、三个本机 TCP 数据进程。128 个不同查询（row 512–639）各重复两次；每种后端 256 个计时请求，客户端并发 4、每节点 1 个计算线程、top-k=10、扩展预算 64、frontier=32、本地 beam=4。详细 trace 开启；每客户端预热 1 次，预热不计入延迟/吞吐。

应用缓存设为 0，OS 页缓存保留。异步每进程最多 8 条在途记录/96 KiB、4 MiB 轮次预约空间；同盘三进程合计 24 条/288 KiB、12 MiB。thread_pool 额外使用每节点 2 个 I/O 线程；io_uring 每节点一个 reactor。

精确真值只针对实际入索引的 4096 个 ID。复用历史缓存前校验数据身份、ID 哈希、query 字节、距离与 self 排除；缓存缺少的条目用原 float64 exact_topk 重新扫描计算，保存在 [exact_truth_additions.json](exact_truth_additions.json)，不纳入查询计时。

## 性能观察

| 后端 | 平均延迟 ms | p99 ms | QPS | 平均 Recall@10 | 失败 |
| --- | ---: | ---: | ---: | ---: | ---: |
| blocking | 31.26 | 55.41 | 126.49 | 0.996875 | 0 |
| thread_pool | 52.76 | 94.39 | 75.40 | 0.996094 | 0 |
| io_uring | 42.26 | 72.00 | 94.13 | 0.996094 | 0 |

三组进程计时窗口的 storage_read_bytes 都为 0；这次没有测到物理 SSD 读量，结果是热页缓存下的功能/开销对照。每请求均扩展 64 个记录、读取 786,432 B（768 KiB）：同步/线程池各为 64 次 pread，io_uring 为 64 条异步独立记录读。批量提交没有减少读取字节或扩展预算。

该负载下同步路径的 p99 和 QPS 均更好，保留同步默认。io_uring 比线程池对照更快，但仍有恢复队列、事件处理和 Python 调度成本。本次只有一种并发/深度/线程配置，按固定顺序运行一次，不足以选择最优参数、证明稳定 p99 改善或推断真实多机冷 SSD 收益。平均召回高于 0.99 只是这 128 个查询的样本结果，重复次数不能当作增加了独立查询数。

远端选择仍使用实测成本和等待时间，因此切换读取后端可能改变普通决策点的动作选择；两种异步后端的样本平均召回比同步少 0.00078125。不能由固定动作一致性推导自适应搜索结果逐条必然相同。没有为批量读取提前派发远端分支。

三组均无不完整资源指标。异步节点收尾时 active_batches、reserved_bytes、inflight_requests 全为 0；峰值在途不超过 8。io_uring 的 4,352 个提交批次中有 172 个涉及多个查询（约 3.95%，含预热），表明跨查询批量提交确实发生，但绝大多数批次仍来自一个查询。没有为了凑批而增加等待。
