# 顶层入口FIFO与广播唤醒的三机对照

完成入口池FIFO预约/定向唤醒实现及回归。相同连接容量下，QPS中位数从293.07增至490.28（+67.3%），p99从3127.57降至580.10ms（−81.5%）；入口平均等待331.51→33.38ms。**这解决了大部分入口饥饿长尾，尚未实现系统等待低于100ms。**

## 控制变量

Intel-35 head/data-0、Intel-32 data-1、Intel-30 data-2；完整seq_2M、32查询线程/节点、总并发128、预算200、top-k10、remote_weight=1。每目标入口连接仍为2，数据间派发与原生回传连接也均为2。临时实验head使用相同实现和单进程发生器，在同一常驻三机数据服务上依次执行broadcast/fifo/fifo/broadcast/broadcast/fifo。每次2000条相同validation查询、预热32条。

两种模式的head都包含本轮新增的连接归还计时，仅`peer.connection_pool.head_scheduling`不同。此阶段数据节点尚未升级，其计算代码和运行进程保持不变；随后三机均发布新版本，另在常驻head上复验。没有多入口进程、减小并发、增加连接数或降低搜索预算。

新计时说明旧版ACK后迟迟不返回，很大部分发生在归还连接时获取共享池状态锁的区间。锁等待包含重新获得CPU调度，不能理解为某个线程长时间独占锁或忙轮询。FIFO先预约名额、再仅唤醒获得名额的请求，减少大量无效唤醒和后来者抢占；数据计算耗时基本不变。

## 限制和负结果

FIFO减少了长时间饥饿，却暴露了后续完成回传/单head处理能力的限制，入口返回后等待报告的区间增大。此区间包括远端计算、结果发送及head处理，不是纯网络延迟。每个模式6000条查询中，API超过100ms的数量从broadcast的2397增加到fifo的5171；因此不能声称所有查询都更快，或系统等待已低于100ms。

3轮是工程重复，未估计置信区间。所有正式节点快照的物理读取增量为0，属于热页缓存测试。实验head与数据节点在各自主机计时，不跨主机相减单调时钟。

最初预热请求因新增head专用配置进入旧数据执行签名而被校验拒绝，没有进入正式计时。已将该字段排除出执行签名、保留所有数据执行参数校验，并补充回归；失败尝试保存在`failed_initial_signature_check/`，不删除也不混入正式结果。

## 实现与复现

FIFO实现位于`python/dhdgs/peer_rpc.py`，head按YAML选择；旧broadcast路径保留。新策略仍使用短锁保护所有权，健康探测、socket关闭和RPC都在锁外。关闭唤醒待处理请求，超时/探测失败/预约竞态均归还对应名额。数据间远程扩展仍只由原启发式决定，计算线程不等待子分支结果。
