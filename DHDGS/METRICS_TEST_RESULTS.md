# 指标实现与本机三节点验证

日期：2026-10-16。已实现的字段与未覆盖部分见 [METRICS.md](METRICS.md)。本轮完成 34 项完整测试；随后对指标边界处理和 CSV 导出补充调整，重跑 9 项相关测试全部通过。

真实数据测试使用三个独立数据进程，地址为 `127.0.0.1:19101–19103`，由中央协调器发起 TCP 请求。服务已在测试结束后停止，没有遗留进程。第一次尝试受沙箱 socket 权限限制，未产生查询结果；获准后完整运行成功，失败尝试的服务日志也已保留。

按用户当前 YAML 的 **RaBitQ 1 bit** 构建了新索引，保留之前的 4-bit 索引。其余采用配置中的 4096 条均匀抽样向量、2560 维、L2、ρ=0.1、top-k=10、frontier=256、扩展预算=256。测试 16 条查询，并发 1，无预热，每条执行一次；没有按结果调整搜索参数。

以上是约一秒的短窗口测试，不是系统饱和吞吐或稳定 p99 成绩。查询为官方查询文件第 0–15 行，已在此前烟测中观察，不可作为新的独立 held-out 证据。未运行 2M 全量索引的性能测试。

按所有查询 wall 时间加权，观察到的时间分解如下：

| 部分 | 占比 |
|---|---:|
| 预处理与路由 | 0.51% |
| 阻塞期间与 pread 调用重叠 | 0.51% |
| 阻塞期间与距离计算重叠 | 10.35% |
| 阻塞期间的数据服务其他处理 | 11.59% |
| 传输、序列化及运行时等等待 | 30.52% |
| 协调线程唤醒等待 | 5.81% |
| 协调器其他 wall 时间 | 40.70% |
| 时钟无法对齐的等待 | 0，本机共享时钟域 |

30.52% 不能全算作网络传输；0.51% 不能全算作物理 SSD 时间；40.70% 也不是精确的 CPU 使用比例。实际 CPU 消耗由独立线程/进程 CPU 指标提供。原始时间分解合计与每条 query 延迟一致，收发字节和、各片精排量与总扩展量、批 trace 数与批次数均已核对。

## 三个数据进程的负载

| 节点 | 扩展顶点数 | 扩展量比例 | 平均使用 CPU 核数 | 结束时 RSS |
|---|---:|---:|---:|---:|
| 0 | 26 | 0.63% | 0.010 | 36 MiB |
| 1 | 3485 | 85.08% | 0.392 | 38 MiB |
| 2 | 585 | 14.28% | 0.088 | 36 MiB |

CPU 观测窗口包含前后管理采样，略大于 query 计时窗口，并受内核 tick 精度限制。三个进程的 `/proc/PID/io` 存储读取字节增量均为 0；文件读取主要命中 OS 页缓存。因此该结果不能用于评估冷缓存 SSD 服务时间或 IOPS。

节点 1 的扩展热点显著强于存储数量倾斜。这是这批少量查询的实测现象，后续应使用更充分、独立的查询样本验证，再讨论负载均衡。每个 RPC 当前重新携带 2560 维查询向量，协议字节还包含服务 trace；后续查询上下文复用和批量策略实验应保持插桩设置一致。
