## 1. 根据已测数据调整优先级

同版本 B2/C 饱和组，每次尝试拉取的查询累计值：

|指标|B2 逐条 post|C 链式 post|
|---|---:|---:|
|拉取批数|1.363|1.360|
|READ 操作数|336.14|334.84|
|记录 READ 阶段 ms|0.140|0.149|
|量化码 READ 阶段 ms|1.522|1.377|
|完成后续跑排队 ms|1.092|1.426|
|完整拉取等待 ms|4.303|4.314|

READ 阶段包含 CQ 调度等待；不能当成纯网卡 RTT。上述部分区间嵌套，不能直接相加。批数和 READ 数不是搜索预算；READ 包括用于候选估距的邻居量化码。

当前 `one_sided.cpp::advance()` 只在当前批内合并重复邻居 ID，随后读取所有这些邻居的量化码。`search_loop.hpp` 在数据到达后才跳过已经装入 `pulled_codes` 的重复码；检索本来还可以使用节点自身和副本 overlay 中的码。因此存在可消除的读取路径，但具体重复比例尚未测量。

下一步顺序：**精确缺失码过滤 → 单边完成与续跑衔接 → 按实测占比决定授权租约 → 用释放的目标余量验证增加接流。** 这修订上一轮初步建议的“先做租约”。每次尝试平均仅 1.36 批，保留首次授权时，租约最多约少 0.36 次批授权，即约 26.5% 此类授权数，尚未扣除释放/撤销消息。不能把所有 335 次 READ 都当成可省的授权 RPC。

## 2. P0：只读取确实缺失的量化码

对一次已批准动作，设其记录邻居 ID 集合为 N，节点本地码集合为 L，固定副本版本中的码集合为 R，当前查询此前拉取并成功安装的码集合为 Q。

```text
missing = N - (L union R union Q)
```

这里的“已有”必须指相同索引代次、量化模型/中心和数据布局下可实际访问的完整码行；哈希相同或 Bloom filter 阳性不能单独充当存在证明。初版只做精确目录查找，不加入跨 query 动态缓存。

具体路径：

1. 搜索线程只在扩展函数批准的原有动作上挂起，将固定副本版本、不可变本地码视图和本次挂起期间只读的查询码视图绑定到请求。
2. I/O 线程 READ 原本需要的记录，解析邻接；对每个邻居做精确存在检查，仅为 missing 生成量化码 READ。
3. 全部依赖完成后恢复同一个查询；延续当前候选估距顺序、去重规则和预算。I/O 线程不能修改候选队列或展开图。
4. 查询执行期间，计算线程仍是唯一计算执行者。版本和视图用生命周期引用固定；取消后在途读取可以排空，但不能安装到另一个查询或新版本。
5. 不根据“曾经 seen”跳过仍需的候选，也不改变已剪枝候选的重发现规则。重复码省读和搜索剪枝是不同优化。

新增计量：邻居逻辑码数、批内唯一数、本地已有数、overlay 已有数、查询已有数、真实缺失数、物理 READ 数/字节、过滤 CPU、安装 CPU。分类按固定优先顺序计数，避免三种已有集合重叠造成重复累计。

先以当前已批准动作/邻接事件做短回放，判断可省比例。若过滤成本抵消收益、缺失码仍接近全部，及时停止，转向数据布局；不能预先承诺大幅降低 READ。

## 3. P1：减少散碎 READ 与续跑成本，分开验证

### 3.1 只合并物理地址相邻的缺失码

缺失码按远端偏移排序，相邻码直接合读；允许小间隙时采用双限制：单次范围最大 16 KiB、总过读比初试不超过 1.25。它们是待验证初值，不是硬件最优值。仅处理已批准记录所需依赖，不提前展开其他远端节点，不人为等后续 query 到来凑批。

判断合读时可用估计：

```text
节省的提交/完成固定成本 > 额外读取字节 / 实测有效带宽 + 整理成本
```

必须统计过读字节、真实有用字节、范围数和整理 CPU。如果地址随机且无相邻区间，保持独立 READ，不扫描巨大间隙。已有 doorbell_batch 只合并 host 提交，和范围合读分别消融；两者不是“一次网络传输”的同义词。

### 3.2 完成数据直接交给唯一计算执行者

目前 READ 完成后先复制到通用 Value 字节数组，续跑时又安装到记录/码容器。计划增加只在单边路径使用的有类型完成结果：记录范围、码行范围、版本和持有缓冲的引用；先消除中间通用字节副本，保留必需的查询码安装。

注册缓冲只有在全部消费者释放后才能复用；按字节额度保留引用，CQ 线程不能等待计算线程释放。容量不足时对新拉取背压，不能覆盖仍被查询访问的数据。不可把“少一次 memcpy”描述为整个路径零复制。

续跑继续使用现有 64 主搜索线程和 8 尾部线程。先记录 `CQ最后完成→结果可用→续跑入队→线程领取→开始安装→计算结束`，判断 1.1–1.4 ms 排队来自目标 CPU 饱和还是任务分配。仅在存在空闲主线程但尾部仍排队时，增加主池空闲时领取尾部任务的机制；当前仅在入队瞬间尝试主池帮助，可能错过随后出现的空闲时隙。

每个续跑任务通过单次原子状态转换领取；取消、尾池、主池只能有一个成功者。按任务/时间额度保证新查询不被尾部饿死。若全部工作线程忙，优先限制额外接流/在途压力，而不声称队列能消除真实容量瓶颈。

### 3.3 小型内存优化单独计量

同源同版本的只读 ID 目录按运行时共享，替代每 QP 一份。当前 16 × 32,000,000 B 可降为一份 32,000,000 B（约 488 MiB → 30.5 MiB）。QP、接收缓冲、完成状态仍独立。此项主要减少初始化流量和内存，不单独宣称能提高稳态 QPS。

## 4. P2：只有控制面证据支持时再做区域租约

先把当前 `pull_network` 拆成授权排队/服务/回复、QP 等待、记录 READ、码 READ 和回调整理。授权占比当前没有独立测量，不能从网络总区间推断其为主要瓶颈。

如值得优化，首次批准拉取时源返回绑定 `(query, owner, source, index_epoch, generation, deadline, byte_cap, record_cap)` 的租约；后续批次在许可和剩余额度内直接 READ。预算始终由查询的唯一计算执行者消耗。

状态协议为：

```text
NONE -> LEASED -> DRAINING -> RELEASED/HANDOFF
```

租约授权与源搜索 actor 首次启动在源侧同一 admission 协议内串行化。收到同 query 的源搜索申请时，先完成冲突协调/回收；不能让副本继续持租约拉取，同时无条件启动源 actor。回源移交必须先停止新增 READ、排空旧操作，再一次性交付剩余预算/已展开集合。正常释放可与已有完成或移交消息合并，但总消息数仍要计量。

取消或过期时停止消费旧完成结果。不能只凭 TTL 过期就把同一份预算再次发给源，同时允许旧副本继续计算。首次实现若无法确认旧执行者已退出，应终止该查询而非无证据重发预算；恢复协议另行验证。MR 暴露整个索引的受信任模型不变，软件租约不能冒充每 query 的硬件内存权限。

原有 RegionVisits 的通知是提示，不能代替源侧权威状态；现有 reserve ACK 也不自动成为可复用租约。WRITE 环形队列和 Task-Push 暂不混入这一变量。

通信优化先要求固定动作/数据字节正确且候选语义不变，再检查端到端质量。稳定QPS提升至少3%可作为初筛目标，但必须超过配对波动/置信区间才能宣称收益；同到达率源runnable不得明显恶化。已有命中Recall低于95%的问题保持开放，不能降低门槛来接受新默认；局部传输收益和整体质量验收分别登记。

## 6. 如何让通信收益成为系统 QPS 收益

当前仅约16.8%–16.9%的全部请求尝试拉取；链式优化还没有改变主要计算回源工作。饱和组所有命中副本后仍计算回源的请求，回源前剩余预算均值约70.7，实际源展开约64.6–64.7。这个群体包含阈值39以外的回源，不能误读成“剩余≤39拉取后预算反而变成71”。

降低拉取开销不保证源瓶颈消失。确认目标副本释放实际CPU/排队余量后，再做独立接流实验：相同图、相同总α和阈值，将条件份额0.8→0.9；若目标仍有余量且源CPU/排队下降，再试1.0。每步短批，有恶化立即停止，保持入口群体一致。

如果通信更快但源CPU/回源实际展开不变、增加接流也无益，则如实结论为“传输优化有效，系统吞吐瓶颈未移动”。下一方向应转向减少高剩余预算回源的覆盖/驻留工作，而不是无限增加RDMA线程或直接启用会增加源距离计算的Task-Push。

## 7. 实现与快速反馈结果（2026-11-02）

本轮 `onesided_missing_20261102` 已实现P0精确缺失码过滤与计量，并独立验证接流0.8→0.9。2K诊断发现98.7%批内唯一码已在本地可用；诊断自身增加查找成本，因此新增`measure_code_availability`开关，后续基线关闭该查找。B1/D1保留为诊断记录，不能据其差值夸大收益。最终36项定向检查通过。

干净30K对照READ减少95.53%、字节减少45.54%。200K饱和：0.8 RPC为13,181.87 QPS；0.9 RPC前后为13,511.04/13,524.52；0.9过滤版为14,518.76，比同份额RPC均值高7.40%。80K同11K/s到达率下，源CPU54.152→50.629核，源runnable p95 4.256→0.028ms。优化版200K仅一次，保留共享机和暖缓存限制；这是本轮观察，不替代长期重复置信区间。

剩余瓶颈改变：饱和过滤版续跑排队累计7.746ms/尝试，控制+READ等0.763ms，码READ仅0.086ms。尾池和主池可能同时满载，暂无证据让空闲窃取消除这个排队。因此本轮未执行范围合读、缓冲直接接管、授权租约或工作窃取；条件接流停止在0.9，没有继续让已饱和副本接更多流量。下一候选为保持总72个计算线程、单独验证主/尾配额分配（例如62/10相对64/8），只改副本节点，源和其他节点保持不变；这属于新实验设计，未执行。

命中计算回源率40.536%→41.571%，尾部额度拒绝829→1580；整体Recall96.6536%，命中94.7058%，质量和回源双目标未通过，默认不变，R001-A29整体继续开放。完整[报告/图表](../test/onesided_missing_20261102/REPORT.md)、[已实现功能](../DESIGN.md#one-sided-missing-codes)、[TestLog](../TestLog.md)。

## 8. 容忍有限召回损失后的优化建议（2026-11-02，设计讨论，未实现或实验）

### 8.1 用户确认的质量约束与实测依据

用户本次明确接受相对当前优化方案，**整体和副本命中群体的Recall@10均最多下降0.5个百分点**。这是后续本方案验收的新约束，取代此前要求命中群体绝对达到95%的门槛；不改写历史实验在当时门槛下的判断，也不自动启用任何默认配置。D200观测值对应示意下限约96.1536%/94.2058%；正式比较须重新运行同期基线，不能把一次历史观测当作精确常数。

固定请求集合、入口策略和随机种子；整体按同一请求逐项配对，副本命中按基线固定群体配对，另报新策略实际命中群体，防止通过改变群体掩盖损失。重复query出现不是独立样本，置信区间按query ID聚类估计；选择参数的校验集合与最终确认集合分离。现有200K回放已用于多轮选择，后续若仍沿用必须标明不是新盲测。0.5个百分点是各群体均值的约束，不是每条query的损失保证。

D200饱和组每个尝试拉取的query累计：续跑排队7.746ms，控制/READ/完成0.763ms（其中授权0.357ms、记录READ0.116ms、码READ0.086ms），安装约0.041ms。各内层区间不得与总区间重复相加。尝试拉取37774/200000≈18.89%；进程CPU源69.58核、副本71.64核、节点1为24.47核。平均计算回源前余额69.64，包含阈值39外的回源；不能假定剩余全部源工作都属于RDMA可处理短尾。

这些数据支持优先减少实际工作、调整计算容量分配和利用轻载节点。不能由7.746ms排队直接推断消除队列就能按比例提高QPS，也不能仅凭占核较低判定第三节点所有资源都空闲。

### 8.2 低成本优先项：尾部收益判断与有界提前终止

保持拉取准入阈值39，另设**进入尾部后累计额外展开上限**，候选初值8/16/24；包括尾部阶段的本地与拉取展开，不只计算远端记录数。这个上限与是否准入拉取的39不同。先用同一短请求集比较当前方案、简单降低全局预算（例如200→190）和尾部上限，确认收益是否只是普通降预算也能得到。

进一步在已批准的源动作前及每次尾部计算批结束处判断：top-k已满、最近若干批结果改善很少、前沿距离估计及经独立校准的误差显示继续改善的可能性低时，结束本分支并汇报已有结果，释放未使用预算，不再因为强制用完尾部额度而读数据。终止必须记录专门原因、舍弃余额、节省读/CPU及质量影响；其他已存在分支照常完成，不能提前宣告整个query结束。

该判断是ANN启发式：当前前沿不够好，不代表经过这些顶点不能到达更好目标；RaBitQ单码误差也不是整次自适应搜索的确定保证。参数必须由配对质量实验选择。第一步只针对≤39尾部，不扩展到高余额回源，以免同时改变过多变量。若QPS收益完全可由更简单的等Recall降预算获得，则采用更简单的方案。

### 8.3 计算调度：固定总线程数、可借用配额与短计算片段

先做仅副本主/尾64/8对62/10的短对照，固定72个计算工作线程及CPU亲和总集合，源和第三节点配置保持不变。分别检查新query排队、尾部续跑排队、上下文拒绝、每请求CPU和QPS。若只是将等待移到主查询，停止扩容尾池；不声称增加尾线程创造了计算能力。

若证据表明固定池隔离浪费可用槽，再设计两类就绪队列共享工作线程、加权分配CPU时间而非简单按任务数分配。普通query保留服务份额，尾部任务按预计剩余计算成本和已等时间选择，防止长任务饿死。只在完整计算批边界让出，首次候选可为8次展开或一个待校准CPU时间片；非逐向量抢占，记录多余入队/恢复成本。

当前主池帮助只在数据就绪回调时尝试，已入尾队列的旧任务不会被随后空闲的主线程主动领取；但本轮主尾可能都忙。因此共享池属于条件方案，非确定收益。查询状态以唯一领取协议移交，I/O完成线程仍不做搜索；本地调度不新增任何未经扩展函数批准的跨机动作。

### 8.4 数据与算法联合优化：邻接先读、原向量延迟精排

当前每次展开先取2560维float32原向量（仅向量即10240B）及邻接，再做精确距离，即便此顶点最终不进top-k。建议实验将远端尾部的导航与精排分离：

1. 仅对扩展函数已批准的记录，先READ邻接段；量化码仍使用精确缺失过滤。固定记录布局中可按偏移读取邻接段，初版不必重建图或复制整套索引。
2. 利用已有RaBitQ码导航，保留有界的待精排候选。没有原向量时不能把近似分数冒充精确距离；结果阈值和候选排序必须显式区分，并作为算法变量测试。
3. 尾部结束或合法交接之前，再按估计值与校准误差选出少量候选，批量READ其原向量并在副本精排。top-k=10可先比较候选上限16/32，上限不是必读数量；已有精确结果和本地向量优先复用。
4. 精排候选必须来自已批准访问的顶点，不越过图扩展决策预取邻居完整向量；读取授权/版本固定持续有效。全部精排READ、排队、CPU及等待计入完成时延，不移到实验后处理，也不以“不消耗展开预算”为由隐藏精排工作量。

大小近似为：原路径每顶点10240B+邻接，新导航路径约4+8×degree字节，再加必要码；最终仍需读取精排候选的10240B向量。如果尾部本来只展开约10点而这些点大多都需精排，额外阶段可能更慢。先对2K样本统计远端展开顶点最终进入精排集合的比例、精确距离CPU及可省字节；比例高或CPU占比很小就停止该方向。必须在相同Recall下与简单降预算比较，不能将少精排造成的质量损失遗漏。

### 8.5 负载均衡方向：由轻载节点执行已批准尾部

当源和副本CPU都高、第三节点仍有实际计算和内存/网络余量时，可将**单个已批准尾部任务的执行权**交给第三节点；由它READ源数据并计算。与把计算推回热点源的Task-Push不同。先测额外状态传输和第三节点准备成本，再决定是否实现完整机制。

这必须成为扩展决策显式批准的合法执行位置，不能由I/O调度器提前派发。移交查询向量、必要候选/top-k、已展开信息、剩余授权与代次；原执行者停止该上下文计算，新执行者获得唯一所有权后才开始，禁止重发整份预算或与源同时执行。原副本的数据依赖不随指针跨机，可携带有限必要码或按授权读取，字节与准备CPU都要实测。

只有预计源/副本排队节省超过移交、第三节点排队和新增读取成本时才选择，并设字节/在途/第三节点CPU额度。若迁移代价过高，更合适的路径是同总α≤0.3的多目标副本布局；两份相同α=0.3副本不符合此约束，不能以复制量翻倍虚报优化。布局与尾部执行位置分别验证。

### 8.6 次优先项及短批验证顺序

- **跨query完整记录缓存与在途同ID请求合并**：先测剩余完整记录READ的跨query重复率，不能用已消除的码重复率替代。按源/epoch/ID共享只读结果，仍保持每query授权和独立预算；缓存/在途字节有界，缓存占用单列且不绕过副本容量约束。此前消息合批的字节去重收益很小，所以没有证据时不优先建设大缓存。
- **单次尾部授权租约**：当前每次尝试约1.33批，首次授权仍需保留，可省批数有限；源actor启动、取消和租约回收协议不可省。暂排在计算和数据量优化之后。
- **增加QP/CQ线程、门铃合批、WRITE控制环**：已有READ及门铃消融不支持它们是当前主瓶颈；除非新计量显示I/O线程或RNIC资源饱和，不再优先扩大参数扫描。

建议顺序：2K离线尾部收益/精排候选审计→当前配置与简单降预算/一个尾部上限的短配对→64/8与62/10单变量对照→只有可省原向量/CPU足够时测试邻接先读→前两节点仍饱和才研究第三节点尾部执行或同容量多目标布局。每步先10K功能/计量再30K A/B/A，若已无明显收益或配对质量损失越界则停止；基线漂移大时先解决可比性。只有入选项进行200K确认与必要重复，避免大矩阵。

QPS优先，但同时验收两个群体损失≤0.5个百分点、零失败、预算/唯一执行权正确，以及固定到达率下的源CPU秒/请求和runnable曲线；饱和时报告三节点CPU、主/尾队列、上下文拒绝及实际回源工作量。提前结束省掉的计算须与副本真正承担的计算分别计量，不能把主动少搜索伪装成等质量卸载。所有建议参数最终进入YAML；本次仅更新研究文档，未改变代码/配置、未启动新实验。

### 8.7 四项实现与实验反馈（2026-11-02）

`tail_four_20261102`已经实现§8四个方向；第四项选择同容量多目标布局，没有实现任意尾部上下文迁移。具体接口、算法约束与功能证据见[DESIGN §63](../DESIGN.md#tail-four-20261102)，完整[报告](../test/tail_four_20261102/REPORT.md)。

快速淘汰：额外尾部上限16的召回损失过大；延迟精排上限8虽省字节，但额外精排/续跑抵消收益；固定总72线程的62/10和共享池单独都未证明QPS提升。原样基线复测从约14.46K变为13.74K，故不将跨批次5%差值全部归因方案。共享池确实降低续跑排队，保留为可选机制。

入口分组采用真实完整h=2邻域、增量重叠成本与工作量平衡；再扩充附着完整一跳块。256个历史入口分成108/148两组，物理总α≈0.2954，包含重复，不双倍复制S30。相同两份图都放节点2约11K QPS；分放到节点1/2约17.4K。200K前后基线13,753.86/13,751.45，分放共享17,428.35，专用尾池17,371.56。共享额外QPS增益只有0.33%，不足证明优越，但续跑排队0.182ms，相对专用池6.891ms明显下降。共享版本p99也非最优（104.84 vs 98.25ms）；保留两份配置。

质量必须配对真实接流群体：旧基线命中Recall约94.68%，新方案原始命中约96.09%，直接说“提高1.4pp”是错误的，因为入口覆盖变了。对新方案实际命中的相同query重算基线，损失约0.411–0.425pp；整体损失0.234–0.245pp。观察均值通过，但按query ID聚类的95%区间到约−0.71pp，不能保证未来损失上限；新接流子群体约损失1pp。全局开关保持可选，未作普遍默认。

源CPU/全体请求降低约20%，源展开110.67→78.90，11K固定负载源ready p95 8.324→0.789ms，三节点CPU更均衡。代价是更广泛接流后的原始回源率39.4%→72.6%、回源剩余预算71→93，以及总CPU/请求略升。旧命中请求的源工作增加，新增接流请求的源工作大幅减少，覆盖扩张带来总体净收益。本轮没有完成“同一批旧命中请求更少回源”的目标，且43秒规划/顺序发布尚不适合很短热点。

下一轮建议以入口为单位估计`源CPU节省/目标CPU与字节成本`，结合源/目标runnable压力及配对质量决定接流份额；将预算优先分给回源过早且净卸载为负的入口，保留完整局部约束。已有READ网络部分不是首要吞吐瓶颈，不继续无依据扩QP。R001-A29保留开放；功能、配置、失败尝试、源码快照与计量口径均在本轮报告/TestLog中。
