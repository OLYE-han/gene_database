# R005 / R010：分支身份、候选合并与预算传递核对

日期：2026-11-04。状态：源码及既有样本审查，非新实验；没有修改运行时搜索逻辑。

用户再次明确：每个数据节点只允许一个查询分支，不能将反复派回原节点作为拉取/派发选择的常规动作。本次先核对既有算法，暂停新的成本模型设计。无副本时按物理节点理解该约束；副本仍须保留此前约定的逻辑区域身份，不能把宿主原片与副本混为同一区域。

## 1. 先前的严格单次访问算法

证据：[DESIGN §7.1–7.3](../DESIGN.md#7-跨机扩展选择函数)，历史提交 `4093380` 的 `DHDGS/cpp/search_loop.hpp`、`native_runtime.cpp` 和 `native_head.cpp`。

- 查询携带 `visited_nodes`；远端候选只在目标尚未访问时有资格触发新搜索。
- 父节点只派发一次，之后 `can_forward=false`、父分支槽位清零，继续自己的本地队列；继续向外派发的权利交给子节点。这是单链启动、各节点本地可并行执行的模型。
- 子节点接收目标入口及其他未访问节点的候选，不接收父节点未完成的本地候选。
- 数据节点接纳表以查询ID去重；同一任务的同内容重试只ACK，不再执行；相同查询的不同分支不能再次进入同一节点。
- 顶层同时检查访问路径、节点唯一性、父子清单、批准决策和预算闭合。N台数据节点最多N次搜索启动，至多N−1次有效跨机启动，重试与心跳另计。

历史提交 `53b3b95` 已加入可配置重访/逻辑区域，但仍有单父一次派发的 `can_forward=false` 路径；不能把不同年代的规则当作同时启用。后来多目标派发属于另一层改动，不要求丢弃“一节点一分支”的用户约束。

原扩展效用按收益/成本并考虑候选等待，概率模式比较本地和最佳远端：

```text
gain(v) = max((T - estimated_distance(v) + kappa * uncertainty(v)) / scale, 0)
          + exploration
utility(action) = sum(gain(v)) / cost(action) * (1 + wait / max_wait)
P(remote) = sigmoid((log(remote_weight) + log(Uremote) - log(Ulocal)) / temperature)
```

本地候选耗尽或等待超过阈值会触发相应远端决策，但仍受访问资格、预算和分支槽位限制。已访问目标不能因为效用高就重新创建分支。实际实现的远端成本主要使用配置RTT、估算消息字节和服务EWMA；文档中的完整远端实时排队模型并未全部实现。

## 2. 当前区域任务保证的是另一种唯一性

证据：[DESIGN §47](../DESIGN.md#query-region-tasks)、[区域目录与收件箱](../cpp/query_regions.hpp)、[接纳和执行](../cpp/native_runtime.cpp)、[搜索循环](../cpp/search_loop.hpp)。这些文件与最新测试冻结源码逐字节一致。

|对象|当前身份/作用|实际保证|
|---|---|---|
|区域执行器 `RegionActor`|查询＋逻辑区域|创建一次，同一时刻只有一个授权在该执行器运行|
|候选收件箱 `RegionInbox`|属于上述执行器|按ID合并候选，搜索批次间取走，按frontier上限裁剪|
|授权记录 `Record`|每次新的 `branch_id`|独立预算、父ID、接纳/启动、搜索调用与报告|
|执行器授权队列 `grants`|多份Record FIFO|当前授权结束后，下一份重新提交计算池|

具体路径：

1. `spawn()`每次生成新的 `branch_id` 并创建子清单，即使目标已有区域执行器。
2. 目标复用 `RegionActor`，把新候选加入同一Inbox，但预算仍放在新的Record中，进入 `actor->grants`。
3. 当前授权可在批次间取走新候选，却仍只使用自己的 `remaining`；它不会直接把待处理授权的预算合入当前额度。
4. `finish_region()`在当前授权结束后，将下一份授权重新提交工作池。因此存在“等待前一授权”与“再次计算池排队”两段。
5. 下一授权调用新的搜索循环，重新构造RaBitQ准备状态、局部top-K、停止状态等。保留了区域身份、Inbox和同机实际展开领取表，但没有持久化整个搜索状态。

所以，“同一区域只有一个活动执行器”并不等同于“查询在该节点只有一个稳定分支及搜索生命周期”。把后续预算授权直接描述为新的独立区域分支会混淆这两个层次；同样，不能用唯一执行器来宣称重复启动、排队与报告开销已消失。

现有测试 `tests/test_region_tasks.py::check_result` 核验同区域 `region_executor_id` 相同、执行区间不重叠、同机展开去重与预算守恒；没有断言每查询每区域只出现一个 `branch_id`。这解释了为什么既有回归通过仍不能覆盖用户此次强调的严格语义。

## 3. 展开预算与分支槽位怎样传递

设某授权获得展开预算B，当前剩余R，剩余分支槽位S。`child_budget_fraction=f`，普通base当前为0.5。

```text
如果还有其他候选组：child_grant = max(1, floor(R * f))
如果只剩目标候选组：child_grant = R
如果还有本地候选且 R > 1：child_grant = min(child_grant, R - 1)
父 remaining -= child_grant                 # 发送前扣除，绝不复制预算

当前多目标模式：child_slots = floor((S - 1) * fanout_child_slot_fraction)
                父 slots -= 1 + child_slots
旧单链模式：    child_slots = S - 1；父 slots = 0
```

展开本身按成功领取且实际处理的顶点数扣减；发现候选、RaBitQ估距、网络发送、单纯读取均不各自消费一次展开预算。拉取数据后在当前节点实际展开，消费当前授权额度；远端分支展开消费转授额度。

每份最终授权报告必须满足：

```text
work_grant = work_spent + work_unused + sum(child.work_grant)
```

顶层递归检查整个授权树。子树展开额度属于祖先已扣除部分，不能把全部 `work_grant` 相加当作查询的实际预算。未用额度当前不自动退还父节点，也没有全局未用额度回收调度。

## 5. 拉取模式额外改变了什么

- `remote_first`在候选选择处使用全体合法候选中的RaBitQ最优顺序，绕过旧的成本效用/随机概率逻辑；该路径也绕过 `min_expansions_after_cross` 的本地驻留限制。仅把YAML里该参数设为16，不能说明本轮拉取模式实际执行了16次驻留约束。
- `switch_after_batches=2`控制连续成功拉取后转授，失败也转授。它没有新增“该目标已拥有本查询分支就禁止创建新的子授权”这一检查。
- `RegionVisits::Snapshot::permits()`对已opened的base区域返回true，表示允许继续合并；当前后续路径仍用新授权承载这次合并。
- 源端拉取授权要求base区域既不在opened，也不在pending，且不存在actor，还要满足源保留权限。故错误字符串 `Pull source active` 不等于“此刻源节点正在计算”：曾经打开但现在空闲的区域也会拒绝。
- 拉取拒绝会将该源加入当前授权的disabled集合，再走spawn转授路径。因此不能只用RDMA耗时与远端排队比较来修复；任务身份和访问资格必须先得到正确表达。
- 当前配置校验要求remote_pull使用可重访区域协议。直接把 `allow_node_revisit` 改为false会被校验拒绝，也无法表达“允许候选合并但禁止新分支”。

## 6. 后续设计的硬边界，尚未实施

先区分三件事：首次创建目标搜索分支、向已有分支补充候选、只读拉取远端数据。它们不能共用“生成新branch_id和子授权”的默认路径。

- 无副本时，每查询每物理节点仅一个规范分支身份；多目标派发可以保留，但不能重复创建已访问目标的分支。
- 已有目标只允许按已确认语义合并候选，不能把合并伪装成新的子分支并反复拆分额度、消耗分支槽位。
- 保留父节点本地继续执行、子节点不携带父本地私有候选，以及全局预算守恒。
- 候选合并本身不增加预算。已有分支如何处理迟到候选、预算用尽、空闲和最终完成，必须明确；不能静默丢弃后声称召回不变，也不能凭空恢复已耗尽额度。如果后续需要在已有任务之间转移额度，须独立设计幂等转移账本与终止协议，不能沿用生成新子授权的方式冒充已解决。
- 代价选择只在合法动作集合内决定拉取或首次派发；不会把“派回原节点再排一次搜索”作为候选方案。

下一步应先补充规范分支身份、补充消息不增分支数/预算、并发首访和终止竞态的检查，再设计拉取与首次派发的成本函数。现有性能结果保留，但不再将“唯一执行器回归通过”称为严格单分支语义已通过。
