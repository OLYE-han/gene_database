# R005 / R010：唯一分支与增量候选同步提案

2026-11-04，设计讨论，尚未实现或开展性能测试。依据[分支与预算审查](R005_BRANCH_BUDGET_AUDIT_20261104.md)，替换对已打开目标反复生成branch_id、子预算授权和搜索调用的路径。本提案不把未实现机制写成DESIGN的已验证能力。

## 已确定的边界

- 用户提出：目标已有本查询分支后，不再为它发起新的RDMA数据拉取；约每10次本地检索同步新增候选、入队距离上界和需要远端计算的点。
- 用户已选择：保持原预算，记录预算不足；本次不做跨已有分支的预算调拨。
- “10次”暂按成功领取并实际展开10个顶点解释，尚未收到对“顶点/搜索批次”问题的明确回答；不计候选发现、估距次数、重复领取和网络回调。实际在搜索批次安全点检查，跨过阈值时发送一次合并增量，不为凑整数10而拆beam；记录真实展开间隔。
- 无副本时，每查询每物理节点只创建一个规范分支。多个目标首次启动仍可并行；同一目标后续只有候选补充。副本身份仍按具体逻辑区域区分，本轮首先验证无LB场景。
- 查询向已有节点发送候选信息不等于再次派发搜索任务。候选同步没有子branch_id、work_grant和branch_slots，不走spawn或grants FIFO。

## 1. 三类同步数据的语义

|字段|内容|接收方动作|
|---|---|---|
|`candidate_delta`|自上次对该目标成功确认以来，新增且尚未通知该目标的候选元数据：ID、同尺度估距、误差量、归属、父点/路径等|按ID去重，将本节点可处理部分与已有frontier合并；不携带2560维完整向量|
|`admission_bound`|发送分支当前候选队列的容量、占用、最差保留候选的估距及ID、状态版本|缓存为发送方向的队列状态提示，用于安排后续向该分支发回候选的次序|
|`remote_work`|当前节点发现、应交给这个已有目标执行的点及请求类型|进入目标既有分支的候选处理流程，用目标原有预算进行排序、精算和图展开；不是无条件强制计算|

`candidate_delta`与`remote_work`可能包含相同ID，在线编码成一张带角色标志的表，避免重复发送。新增候选通知表达发现事实；`remote_work`表达已有搜索策略批准交由目标处理的工作。网络模块只搬运记录，不自己决定开始远端搜索。

按目的分支整理消息：B只接收与B执行区域有关的增量；A本地私有候选不交给B计算。初版不把所有节点的完整frontier互相复制，也不向尚未启动搜索的节点发同步消息。对于仅供其他分支参考的非归属候选，保持为提示元数据，不自动计算或继续广播。

同步得到的条目不因再次入队就原样转发回来源，使用来源和已确认发送记录去重，避免A↔B反复回声。发现的新邻居是新条目，可以按归属发送。多归属顶点按既有规则选择处理目标；本协议不声称已经实现跨物理节点全局原子领取。

## 2. 入队距离上界必须区别于结果top-K阈值

当前候选排序是 `(estimated_distance, global_id)`，容量由 `search.frontier_size` 决定。暂沿用此排序，不在协议中暗中改成另一种不确定度分数。

```text
U_i = +infinity                         if frontier_i.size < frontier_capacity
U_i = max(estimated_distance(v))        otherwise
```

还须同步同距离时最差候选ID和状态版本，匹配实际tie-break。这里的“上界”只是当前队列可接纳分数的门槛，不是查询真实近邻距离的数学上界，也不是结果集第k名精确距离。

重要限制：队列展开并移走元素后会出现空位，U_i可能放宽，所以不能取历史最小值；不同节点负责不同区域，也不能直接把 `min(U_i)` 作为全局永久剪枝线。RaBitQ估距还包含误差，桥接点本身距离较远也可能引向更近区域。

初版只用远端缓存U决定同步包内优先级，或按新鲜度辅助合批，不用它永久丢弃`remote_work`。接收方按自己的实时frontier容量、当前比较规则和预算作决定；正常ANN容量裁剪要单列计数。不能用本地A的入队门槛替代B的实时门槛。

## 3. 何时发送，以及消息如何可靠抵达

每个规范分支维护实际展开计数和按目标划分的增量缓冲。常规触发为累计展开跨过下一次10点阈值，在批次末提交当前增量；同时到期的多个阈值只合并一次。不发送没有候选增量、没有必要状态变化的空包。

建议增加以下补发条件，均是已批准工作的交付，不是提前批准新扩展：

1. 本地候选暂时耗尽、预算耗尽、准备进入空闲或结束时，立即发送未达10点的剩余增量。
2. 有待发工作却因I/O或缺候选无法达到10点时，网络模块按可配置最大滞留时间补发；只处理已提交的缓冲，不遍历图或调用扩展决定函数。
3. 到达包条数/字节上限时拆包；没有新数据不周期性重复整个队列。

搜索线程在批次末将有界增量发布给独立发送模块，继续自己的搜索或释放线程，不等发送或ACK。发送者负责组包、传输、重试；接收线程只做身份校验、幂等接纳、写收件箱和回复。

消息头包括query/token/索引epoch、源和目标规范branch_id、单调序号、状态版本。对每个目标分别维护确认水位；只在接收方明确接纳/拒绝后释放对应条目，乱序接收不能跳过尚未抵达的序号。重试复用原序号与内容，不生成新查询工作。

目标不存在、仍在首次创建途中或已经全局结束时，返回明确状态；同步处理器不得顺手创建分支。首次派发后仍在途的读请求需要排空/完成原批准动作并记录，之后不再新发该目标的拉取；禁止取消后把该批额度和候选静默丢弃。

对已批准remote_work不能因网络队列满静默丢弃：保存在有界待发区重试；待发区也满时在安全点挂起当前上下文并释放工作线程。普通候选的容量裁剪遵循明确的ANN规则并统计，不能隐藏为网络成功。

RDMA仍可用于这些控制/候选消息的传输；“不再RDMA拉取”指不再把该目标的数据记录拉来本地计算，不要求把同步消息改成TCP。

## 4. 接收合并、唯一分支和原预算

规范分支持久保存同一frontier、实际展开领取表、top-K、RaBitQ查询准备状态、remaining和同步版本。保持一次一个计算线程，不并行执行这个分支。

```text
收到同步消息：
  校验 query + canonical_branch + epoch + sequence
  重复消息 → 返回原回执
  目标未创建/已全局结束 → 返回明确状态，不创建任务
  原剩余预算为0 → 记录唯一未处理点，回 budget_exhausted
  否则 → 合并到该分支的Inbox，回接纳结果

既有分支正在运行 → 下一个批次安全点合并
既有分支在等待I/O → 缓存，原续跑时合并
既有分支暂时空闲且有预算 → 原身份/原状态恢复，不生成新授权
```

接收方区分已展开、已入队、实时frontier裁剪、预算不足和查询终态。`budget_exhausted`不是网络失败，不无限重试，不转回RDMA拉取，不生成新分支，不增加预算。消息接纳表示候选被纳入处理范围，不承诺它一定在有限预算内展开。

首次创建未访问节点时，仍按原规则从父remaining中扣除子预算；候选同步不再执行这个动作。全局不变量仍是初始预算等于各规范分支最终展开、最终未用及在途首次派发额度的守恒账目，终态时在途额度必须结清。不能把首次分配额度和子节点实际展开重复相加。

接收方用完预算之后，候选可能被明确跳过，因此Recall仍需实测。初版不做剩余额度调拨；“没有预算超限”和“不会降低召回”是不同的验收项。

### 4.1 目标还在计算队列中时如何同步

2026-11-04补充，针对用户提出的长排队问题，仍为设计讨论、尚未实现。同步采用异步增量交付，不要求两个分支同时运行，也不要求双方每完成10次展开相互等待。

必须区分三个事件：接收方已接纳消息、候选被计算线程消费、顶点实际被展开。接收ACK只确认第一个事件，不能作为后两者的证明。

|目标状态|接收与发送路径|计算路径|
|---|---|---|
|首次派发还未确认接纳|源端保留同一规范身份及有界待发增量，查询接纳状态或幂等重试首次派发；不得创建另一分支|不把不确定的子预算拿回本地重复消耗；普通同步不能隐式建立目标|
|已接纳、计算尚未开始|接收线程向该分支Inbox写入增量，按ID合并并独立回复接纳/裁剪状态|只保留一个待运行任务；每个同步包不能再生成计算排队项|
|正在计算或等待I/O|接收路径继续缓存、确认|下一个批次安全点或原续跑时合并|
|空闲且有预算|合并候选后，原分支至多排入一次续跑|恢复原状态，不产生新授权|
|预算耗尽|明确回复预算不足，统计唯一未处理候选|不追加预算、不另开分支、不改走数据拉取|

首次接纳只建立必要上下文、收件箱和唯一计算排队项，回执不依赖实际获得计算线程。接收模块与计算池分离；Inbox采用短临界区或单拥有者队列，解码、传输、图展开和长耗时初始化不持有收件箱锁。接纳本身仍有CPU、网络和容量限制，不能保证无等待，须独立测量。

示例：A展开10点后发送增量；B仍排队，但B接收线程确认已存入；A继续运行；B后来获得工作线程，首次取走当前积累的候选并按实时规则排序。B没有展开过顶点时，只能报告“已接纳、正在排队、展开数为0”，不能提供尚不存在的新邻居或伪造新鲜上界。尚未初始化的上界标记无效；旧上界携带版本/有效性，仅作提示。

回执与监测分别记录`received_seq`、`consumed_seq`、`expansions_done`、`remaining`、分支状态和上界版本。消费序号只表示该批已被合并/明确裁剪，不表示其中所有点都已展开；序号水位不能跨越缺口。确认排队状态不触发重复派发。控制线程可批量反馈这些状态，源搜索线程不等待反馈。

有界Inbox不能无条件确认所有新增点：同ID可合并，正常ANN容量裁剪须在回执/计数中明确表示；容量不足且无法按规则接纳时返回背压，源网络模块保留未确认条目。源待发区也满则按第3节挂起上下文、释放工作线程，不能用无界内存隐藏长排队。查询取消与失败仍须显式结清预算和在途消息。

### 4.2 异步接纳不能消除计算排队

如果A先用完原预算，而B很晚才返回新候选，A按用户选择记录预算不足，不恢复新额度。若A只是暂时无候选且仍有预算，则释放工作线程并保留上下文，晚到候选恢复原分支。顶层不能因为A先结束便漏掉已经提交的B；最终完成仍必须等待B或明确的失败/取消处理。这是查询依赖等待，不是搜索线程忙等。

因此需要分开评估两项后续设计：

1. **首次派发前的选择**：仅对尚无分支的目标，把远端预计计算排队加进首次派发成本，并与RDMA拉取、原节点续跑排队及计算成本比较；目标已接纳后仍遵守不再拉取/不重建分支的约束。队列长度本身不够，需要服务速率、剩余工作量与观测新鲜度；估计不准确时记录误差，不能保证预测最优。
2. **既有唯一分支的公平调度**：考虑以原查询年龄及本次就绪等待时间共同防止下游分支反复排到新查询后面。不能每收到一个候选包就增加任务或无限提优先级；需有限计算片段、老化及新查询公平份额。此项是待实验调度方案，不在候选同步协议中默认启用，也不增加搜索线程或预算。

收件箱解决“消息必须等计算才能送达”，公平调度解决一部分不必要的排队；当工作到达率超过计算服务能力时，两者都不能承诺等待始终低于100ms。需区分突发拥塞、持续过载和调度不公平，不以降低测试并发冒充同负载性能提升。

补充测量：首次派发接纳耗时、增量发送至接纳耗时、接纳至消费耗时、首次/续跑计算排队、最老待处理候选年龄、Inbox/待发区峰值和背压、因晚到而预算不足的查询比例及唯一候选数；跨机单向计时须注明时钟误差，优先用各节点本地单调时钟分段和发送端ACK往返计时。

## 5. 释放计算线程与查询最终结束要分开

空队列时立即释放工作线程，但保留唯一分支的内存状态。后到候选有原预算可用时，只恢复该分支；不能重新建立父子授权链。预算耗尽也立即释放线程。

当前父子授权树的“一份报告即终态”不能原封不动用于可恢复分支：A暂时空闲后可能收到B的最后一批候选。结果可按版本先上报，但顶层只能在候选消息已经结清、所有分支静止后给出最终结果。报告版本更新不等于创建新的查询分支。

首版建议在顶层已有终止管理中增加仅发生于收尾的静止确认，不能靠“等1ms大概没消息”判断结束：

1. 顶层收到所有已注册分支的空闲/预算耗尽状态，且首次派发清单已闭合，发起带epoch的收尾探测。
2. 数据节点在同一分支状态同步点检查：无可执行候选、无未消费Inbox、无在途I/O、无待发/未确认候选消息；满足后暂时封住该分支的新发送并回复prepared。
3. 封口后若遇到真正的新候选，不确认成功，回本轮收尾无效/重试；有未确认发送的节点无法prepared，顶层撤销本轮探测后恢复处理。重复的旧序号仍可幂等确认。
4. 只有所有参与节点均prepared才commit；新任务/迟到消息竞态使本轮abort，状态保留。整个过程不占搜索工作线程。

这会引入收尾控制消息，必须单独测量开销；它不是对已有实现已正确的断言。后续可研究更轻的分布式终止记账，但本提案不以不可靠超时省略在途消息处理。

## 6. 参数草案

以下仅为提案示例，尚未接入schema，不能直接并入运行配置。10为用户建议阈值，其他数值只是待测起点。

```yaml
peer:
  candidate_sync:
    enabled: true
    interval_expansions: 10
    flush_at_batch_boundary: true
    max_delay_us: 1000
    max_records: 64
    max_bytes: 16384
    flush_on_idle: true
    flush_on_budget_exhausted: true

```

目标分支已打开后是否禁用拉取、是否禁止新branch_id、是否不附带预算等是协议不变量，不作为可随意混搭的性能开关。最大滞留时间只能补发已获准的候选同步，不能启动未访问目标。

## 7. 需要验证的收益与风险

目标收益：消除同节点新授权FIFO、重复查询准备/top-K初始化和逐授权报告；仍在运行的目标可在下一批直接消费新候选；减少把向量拉回来的字节。恢复空闲分支仍可能等待计算池，首次计算排队也不会因此自动消失。

新开销：更频繁的小消息、Inbox合并、收尾确认，以及固定预算造成的未处理候选。D200、间隔10时，纯计数触发总次数不超过20；向其余两个活跃目标分别发送时最多约40个包，未含拆包、补发、确认或重试，因此不能直接承诺RPC下降。实际稀疏消息可能远少于该数，须测量。
